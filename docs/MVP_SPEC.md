# ТЗ: помощник ведущего, MVP

Дата: 2026-09-15. Источники: `DnD.pdf` и обсуждение проекта.

**Обновление 2026-09-16:** этот документ сохраняет требования первой версии с подготовленными исходами. Для нового режима действует [ТЗ свободного мира с LLM](FREE_WORLD_SPEC.md): основной провайдер Codex CLI по подписке ведущего, альтернативный API с лимитом $5 на сессию, обычный исход принимается ведущим одним нажатием, свободные действия проверяются по фактам и общим правилам. Новое ТЗ описывает следующий этап, а не уже реализованную функциональность.

## 1. Согласованные решения

- Все участники, включая ведущего, — новички. Ведущий управляет игрой и видит секреты.
- Первый прогон: 30–40 минут, один ведущий и один либо два игрока.
- Приложение, база, веб-интерфейс и Telegram-бот работают на ноутбуке с Windows 10 или 11.
- Разработка ведётся на Linux. Ведущему нужен простой запуск на Windows; предполагаемый канал передачи — GitHub. Ключи пользователь передаёт отдельно.
- Ведущий открывает веб-экран. Игроки отправляют обычные голосовые или текст боту и получают карточку персонажа и запросы бросков.
- Используется внешний GPT API; пользователь сообщил о наличии доступа. Работоспособность ключа, доступность конкретных моделей и распознавания ещё не проверены.
- Первоначальный ориентир расходов API — до $1 за тестовую игру; платный сервер не нужен. Для API-вызовов нового свободного режима 2026-09-16 согласовано $5 на сессию; основной провайдер нового режима — Codex CLI; настройки прежних игр этим документом не меняются.
- Упрощённые правила описываются на 1–2 страницах; создание персонажей, уровни и развитие исключены из MVP.
- Модель предлагает решения и формулировки. Программа выполняет расчёты, проверяет переходы и хранит факты.
- Принятие итогов, ручное решение ведущего, сохранение, восстановление и отмена входят в MVP.
- Другие правила и интерфейсы должны подключаться через выделенные границы, без переписывания игрового ядра.
- Это учебный проект для портфолио при подаче на Ausbildung. Ведущий должен получить исходники и возможность участвовать в последующей разработке. Направление пока не выбрано; проект не привязывается к подготовке именно программиста. Его опыт программирования ещё не уточнён.

Документ, правила и приключение приняты пользователем как основа первого прототипа. Первая реализация ядра, веб-интерфейса и адаптеров готова. Этот документ описывает целевой MVP: актуальная готовность и ограничения перечислены в [README](../README.md). Подробности упаковки — в [плане передачи](DISTRIBUTION.md).

### Расширение: собственные сценарии

В продукт входят промпт с контрактом, локальная проверка JSON, отчёт для исправления в том же чате, библиотека и выбор приключения. Сценарий закрепляется в сохранении партии. Подробный действующий контракт — [ADVENTURE_FORMAT.md](ADVENTURE_FORMAT.md).

Это расширяет первоначальное ограничение одним приключением: поддерживается `declarative@1` с настраиваемыми героями, характеристиками, кубиком, действиями, условиями, эффектами и финалами. Первая живая проверка остаётся на 1–2 игроках; формат допускает до шести. Импорт текста полной редакции правил не заменяет программный исполнитель этой редакции. Визуальный редактор остаётся вне текущего объёма.

## 2. Цель и объём

### Очерёдность дальнейшей работы

После прохождения текущего демо сначала исправлены три замечания пользователя к списку действий и переходам. 2026-09-16 пользователь поручил перейти к свободному миру и подготовить [обновлённое ТЗ](FREE_WORLD_SPEC.md). [Ближайшие задачи](NEXT_STEPS.md) и [исходная концепция](HYBRID_WORLD.md) зафиксированы отдельно. Остальные проверки удобства интерфейса сохраняются, но не блокируют новый этап. Описанные ниже возможности первой версии не означают, что свободный мир уже реализован.

Ведущий без знания правил проводит короткое приключение, следуя понятным подсказкам. Основное действие на экране всегда одно: запросить бросок или продолжить после прочтения результата.

Вторая цель — передать сопровождаемый учебный проект: будущий участник может запустить исходники на Windows, разобраться в одном игровом шаге, внести изменение и проверить его. Пользовательский запуск готовой программы остаётся отдельным простым сценарием.

Включено: одна активная сессия на установку, встроенное приключение с двумя готовыми персонажами, импорт и библиотека собственных приключений, последовательная очередь действий, проверки и короткий бой, журнал, сохранение, отмена, учёт расходов и задержек.

Исключено: публичный сервис, платежи игроков, редактор приключений, импорт книг правил, переключение системы посреди игры, карты и перемещение по сетке, генерация изображений, синтез речи, постоянное прослушивание стола, Telegram Mini App, автономный ИИ-ведущий.

## 3. Подключение и роли

1. Ведущий запускает приложение, открывает локальную страницу и создаёт сессию.
2. Приложение показывает временные приглашения для игроков и отдельную привязку Telegram ведущего.
3. Игрок открывает приглашение в личном чате с ботом и выбирает свободного персонажа.
4. Приложение закрепляет Telegram user ID за участником сессии. Имя и username не являются удостоверением роли.
5. Ведущий начинает приключение, когда подключились один или два игрока.

Карточка и текущее ожидание восстанавливаются после перезапуска. Два пользователя не могут занять одного персонажа. Бот обрабатывает игровые команды только привязанных участников.

Роль и разрешения проверяет сервер. Игрок получает только свою карточку, свои запросы и общедоступные открытия. Секреты не включаются в Telegram-сообщения игрокам.

## 4. Игровой шаг

Состояния: входящее действие → подготовка предложения → ожидание броска (если нужен) → готовый итог → принятие.

- Полученное сообщение сразу распознаётся и подготавливается к обработке; отдельное «Принять действие» перед подготовкой не требуется.
- Только первое действие очереди получает предложение на актуальном состоянии. Последующие ждут; их нельзя заранее разрешать по устаревшей сцене.
- На экране видны автор и краткое содержание. Автор сообщения и персонажи, выполняющие действие, различаются.
- При проверке основная кнопка — «Попросить бросок». Нажатие фиксирует действие, параметры проверки и запрос конкретному участнику.
- Без проверки сразу показывается готовое последствие.
- После броска программа автоматически считает результат и готовит итог. Отдельных кнопок расчёта и подтверждения числа для программного броска нет.
- Основная кнопка «Продолжить» принимает итог и применяет связанные изменения одной операцией.
- До принятия показывается короткая строка изменений, например «Открыта улика: сердечник сняли вручную».
- «Исправить», «Другой вариант», «Решить самому» и «Пропустить» — дополнительные действия.
- Повторная генерация меняет формулировку при сохранении броска и допустимого исхода. Она не позволяет перебрасывать кубик или менять успех на провал.
- Переход в следующую сцену выполняет ведущий; модель сама сцену не закрывает.

Если сообщение неоднозначно и это влияет на исход, приложение задаёт один конкретный вопрос. Не требуется уточнение несущественных деталей.

## 5. Интерфейс ведущего

Центр: текущий шаг, текст для чтения, следующая реплика ведущего и одна основная кнопка. Секреты и объяснение механики раскрываются отдельно.

Дополнительно: очередь, карточки персонажей, сцена, NPC, открытые улики, журнал, «Помоги продолжить», «Пауза», «Отменить последний шаг».

«Помоги продолжить» предлагает вопрос или доступное направление и не меняет мир.

Ведущий может внести своё решение текстом или голосом через привязанный Telegram. В боте он выбирает режим «Действие группы» или «Мой исход». Голосовой исход преобразуется в предлагаемое событие и показывается перед принятием. Изменение закреплённого факта требует отдельной явной правки ведущего с записью в журнал.

## 6. Telegram и голос

- Общение происходит в личных чатах с ботом.
- Меню игрока: «Персонаж», «Инвентарь», «Что я умею», «Открытия».
- Карточка показывает HP, бонусы, предметы и действия простым языком.
- Голосовое скачивается во временное хранилище и отправляется в сервис распознавания. Затем временный файл удаляется; приложение сохраняет текст.
- Удаление временного файла не означает удаления сообщения в Telegram или данных у провайдера API.
- Распознанный текст показывается игроку и ведущему. Исправление доступно, но не является обязательным подтверждением каждого сообщения.
- Пока запрос броска не отправлен и итог не принят, исправление заменяет действие и отменяет старое предложение. После этого требуется явная отмена шага ведущим.
- Предлагаемое ограничение голосового — 60 секунд. Превышение или ошибка распознавания возвращает понятную просьбу сократить запись либо отправить текст.
- Программный d20 генерирует сервер по кнопке бота. Результат закрепляется за запросом, повторное нажатие возвращает то же число.
- Для физического кубика игрок вводит выпавшее число 1–20; модификатор прибавляет программа. Такой бросок отмечается как введённый вручную.

## 7. Состояние, правила и ИИ

Разделить:

1. Версионируемое приключение: локации, NPC, секреты, препятствия, заранее подготовленные исходы.
2. Состояние сессии: участники, персонажи, сцена, открытые факты, активный запрос, версия состояния.
3. Журнал принятых событий и отмен. Отклонённые ответы хранятся только как диагностические записи и не становятся памятью мира.

Каждая сессия закрепляет ID и версию приключения и правил. Смена редакции для уже начатой сессии не входит в MVP.

Модуль правил определяет структуру характеристик и их отображение, доступные действия, проверку допустимости, расчёт бросков и разрешённые эффекты. Ядро сессии отвечает за роли, порядок шагов, сохранение и доставку результатов. Интерфейс не содержит формул проверок и урона.

Для новой редакции допустимы новый модуль и расширение отображения карточек. Универсальный конструктор всех систем не требуется.

ИИ вызывается через отдельный интерфейс провайдера. Распознавание речи и генерация текста имеют независимые настройки моделей. Конкретную модель выбираем после проверки русского текста, имён, скорости и структурированных ответов.

## 8. Защита от ошибок модели

- Модель получает актуальное состояние и релевантные факты, а не восстанавливает их только из истории чата.
- Ответ проверяется по схеме и предметным ограничениям: существующие ID, роль, текущая фаза, допустимые действия, основание каждого эффекта.
- У модели нет прямого доступа к записи в базу. Текст игрока не может менять правила, роли, HP или результаты бросков.
- Бонусы и вычисления выполняет модуль правил. Для подготовленных препятствий сложность и последствия заданы приключением.
- Свободные описания не должны вводить новые предметы, опасности или улики. Значимые новые факты оформляются отдельным предложением; в подготовленных сценах используются заданные факты.
- Текст для чтения формируется из разрешённых к раскрытию сведений и проверенного исхода. Скрытые факты передаются только этапу подготовки решения, когда нужны ему.
- Ключевые улики, механические результаты и запасные ответы имеют готовые формулировки. Свободная генерация не гарантирует отсутствие всех смысловых ошибок; это проверяется игровыми сценариями и наблюдением.
- При невалидном ответе — максимум одна автоматическая попытка исправления, затем готовый ответ на основе проверенного исхода. Если допустимый исход неизвестен — один вопрос ведущему и ручное решение.
- При изменившейся версии состояния старый ответ не применяется.

## 9. Сохранение, отмена и сбои

- Принятие события, изменение состояния и задания на отправку сообщений сохраняются атомарно.
- Входящие Telegram updates и команды имеют защиту от повторной обработки. Повторная доставка не дублирует бросок или эффект.
- Запрос броска сохраняется до отправки. После сбоя приложение восстанавливает запрос и уже полученный результат.
- При неудаче GPT, распознавания или сети игровое состояние сохраняется. Видны конкретный статус и доступный следующий шаг.
- Отмена сначала убирает незавершённое предложение/запрос, затем позволяет отменить последний принятый шаг. Его эффекты снимаются, зависимые запросы перестают приниматься, карточки обновляются.
- Уже увиденную игроком тайну отмена скрыть из человеческой памяти не может; такие отмены отмечаются в журнале.
- Восстановление не проигрывает автоматически накопившиеся во время паузы действия: очередь видна ведущему.
- База копируется перед запуском новой игры и после завершения. Экспорт сохранения доступен для переноса на другой компьютер.

## 10. Локальное размещение и бюджет

Предлагаемая реализация: один локальный сервер приложения, SQLite, веб-интерфейс и фоновый Telegram polling. Вызовы GPT и распознавания выполняются с сервера через интернет. Модели локально не запускаются.

Веб-сервер по умолчанию слушает только loopback, не открывается в локальную сеть или интернет. Для изменяющих запросов проверяются локальная сессия и origin. Для переноса на хостинг потребуется отдельная настройка HTTPS и доступа.

Ключ API и токен бота задаются локально вне репозитория. Экран первой настройки принимает их однократно, не сохраняет в browser storage и не возвращает сохранённые значения в ответах API. Они не попадают в Telegram, журналы, сборки и экспорт игры. Поставляется запуск с понятной проверкой конфигурации; пользователь не должен вручную запускать несколько процессов.

Разработчик запускает исходники на Linux; ведущий получает готовую сборку Windows, запускаемую без установки Python, Node.js, Git, Docker или WSL. Приложение само запускает сервер и бота и открывает локальную страницу после готовности сервера. Ключи и сохранения находятся в пользовательском каталоге отдельно от папки распакованной программы; обновление пакета их не перезаписывает.

Для GitHub предусматриваются тесты на Linux и Windows, сборка Windows-пакета на Windows runner и прикрепление проверенного архива к выпуску. Сборка не требует настоящих API-ключей и токена бота. Первая целевая архитектура пакета — Windows x64; другие архитектуры отдельно проверяются при необходимости.

Предлагаемый бюджет сессии — $1. Учитываются запросы распознавания, входные, выходные и оплачиваемые токены рассуждения, а также повторные запросы. Цены хранятся в настройке с датой актуальности.

Перед вызовом резервируется оценка стоимости с учётом лимита ответа; после вызова она уточняется по usage. При исчерпании доступного бюджета новые платные вызовы останавливаются, сохранение и ручное ведение доступны. При неизвестной цене автоматический вызов не выполняется до настройки. Учёт приложения не заменяет счёт провайдера и не гарантирует точного ограничения банковского списания.

Отдельно измеряются: доставка Telegram, распознавание, подготовка решения, генерация текста и число исправлений. Предлагаемая цель: 90% обычных действий получают готовую подсказку в течение 10 секунд после получения сообщения сервером. Это цель проверки, не обещанная характеристика; загрузка голосового на стороне Telegram считается отдельно.

## 11. Приёмка

- Игра проходит от создания сессии до финала с одним и с двумя игроками.
- Участники действуют через Telegram, ведущий получает инструкции без предварительного чтения правил.
- Без броска нужен один основной клик ведущего, с броском — два; исключение — неоднозначность или ручная правка.
- Есть успешная и неудачная проверка, мирное разрешение и короткий бой.
- Физический и программный броски проходят одинаковые расчёты; повторные кнопки и доставки не создают второй результат.
- Секреты не присутствуют в данных, отправленных игрокам. Ключевые тексты не раскрывают улику до допустимого события.
- Перезапуск проверен во время ожидания броска и после его получения до принятия итога.
- Отмена корректно восстанавливает HP, предметы, открытые факты и очередь зависимых операций.
- Проверяются провокации: несуществующая способность, лишний предмет, выдуманный урон, просьба игрока игнорировать правила, преждевременное раскрытие секрета, запоздавший ответ модели.
- Проверены ошибки API, распознавания, исчерпание бюджета и ручное продолжение.
- После прогона доступны фактическая стоимость, задержки и число исправлений ведущим.
- Готовый архив запускается на Windows 10 и 11 x64 без инструментов разработки и прав администратора; отдельно проверяются пути с пробелами и кириллицей.
- Первая настройка, повторный запуск, остановка и обновление проверяются на готовой сборке. Повторный запуск не создаёт второго процесса Telegram polling.
- Исходники, релизный архив, диагностические сообщения и экспорт игры не содержат ключей; новая версия сохраняет настройки и игру.
- Полный исходный код, описание зависимостей, инструкции разработки для Linux и Windows, команды тестирования и сборки передаются вместе с проектом. Инструкции сверены с реальными командами после реализации.
- Режим тестовых провайдеров позволяет выполнить полный демонстрационный игровой шаг без платного API и Telegram; отсутствие внешних интеграций обозначается явно.
- Подготовлены короткая карта модулей, объяснение пути одного действия и небольшие задачи для самостоятельного участия. Пример задачи проходит путь «описание → изменение → проверка → ревью».

## 12. Последовательность разработки

1. Каркас локального запуска на Linux и упаковки для Windows; затем ядро сессии, данные приключения и правил, сохранение, отмена. Проверки инвариантов и механики.
2. Экран ведущего и полный игровой шаг с тестовым провайдером ответов.
3. Telegram: приглашения, роли, карточки, текст, броски и повторная доставка.
4. Распознавание голоса, GPT, проверка ответов, запасные исходы и учёт расходов.
5. Готовый Windows-пакет, короткая инструкция ведущему, восстановление после сбоев и сквозной прогон на 30–40 минут.

Для интеграционной проверки потребуются локально настроенные API key и токен созданного пользователем Telegram-бота. Они не нужны для подготовки ядра, интерфейса и тестовых сценариев.
