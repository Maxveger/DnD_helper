# Путеводитель по документации

Состояние на **2026-09-22**. Активный эксперимент — игровая IDE со строгой живой игровой беседой, отдельным подтверждением ведущего и независимым режиссёрским наблюдателем. Лабораторный маршрут `/studio` для среза «Сайрус → Дом → Око» дважды пройден с Luna; второй щадящий прогон завершился без технических повторов и подтвердил направление как промежуточный успех. Наблюдатель уже реализован в исходниках и проверен на подставной модели: он видит подтверждённую игру, но может повлиять на игровой слой только через явное одноразовое решение ведущего. Его живой прогон ещё не выполнен. Прежние `/world` и подготовленный режим сохранены отдельно. Опубликованный Windows-кандидат `v0.1.0-rc.1` относится к прежней версии.

## Как читать статусы

**Текущая документация** описывает поведение исходников. **Отчёт** фиксирует конкретную проверку, а не обещание будущего результата. **Прежний режим** продолжает работать отдельно. **История решений** объясняет путь проекта, но не задаёт текущую очередь разработки.

При расхождении приоритет: [решения пользователя](PROJECT_BRIEF.md) → [игровая IDE](GAME_STUDIO.md) → [план](NEXT_STEPS.md). Документ прежнего помощника [GM_ASSISTANT.md](GM_ASSISTANT.md) применяется только к `/world`. Форматы и ограничения сверяются с кодом. Старое ТЗ не переопределяет эти документы.

## Как поддерживать порядок

- Описание поведения обновлять в тематическом документе; в путеводителе хранить назначение и ссылку.
- Решения пользователя — в основе проекта, текущую очередь — в следующих шагах, результаты измерений — в отчётах.
- Указывать режим и статус: реализовано в исходниках, проверено на Linux, проверено на Windows или опубликовано.
- Новую страницу добавлять в подходящий раздел этой карты и связывать с соседними темами. Исторические отчёты не переписывать как результаты новой проверки.
- Промпт и JSON Schema текущего мира получать из приложения: они формируются по моделям кода. Не поддерживать вторую ручную копию схемы в Markdown.
